# KAIST Drone Localization 성능 최적화

## 입력과 비교 조건

이전 측정의 Temp AVI는 재접근할 수 없었다. 새로 생성한 320 × 240 MJPG AVI를 동일 PC에서 최적화 전후에 사용했다. 기준 영상은 seed 42, 목표 (1.73, 2.02) m, yaw 37°에서 생성한 합성 프레임을 25 FPS 시간표로 기록한 것이다. [입력 해시와 생성 설정](input/manifest.json)

최적화 전 네 주기는 기존 순서로 각각 60초씩 측정했다. 같은 설정의 최적화 후 콜드 스타트 비교는 Unlimited만 60초 다시 측정했다. 별도의 최적화 후 시험은 OpenCV 1스레드, 4초 워밍업, 60초 측정, 시드 42로 순서를 회전하는 프로토콜을 사용했다. 구간 외 결과는 CSV에 `drained`로 표시된다. 각 반복 JSON에는 실행 시각, 환경, 해시, 메모리와 CPU 사용률이 들어 있다.

이 PC의 프로세서는 Intel Core i7-1165G7이고 OS에서 논리 CPU 8개를 보고했다. 측정 환경은 Windows, Python 3.11, OpenCV 5.0.0(Concurrency), NumPy 2.4.6(OpenBLAS)였다. 프로세스 CPU의 100%는 논리 CPU 한 개 시간이며, RSS는 벤치마크 구간 양 끝에서 읽은 프로세스 작업 집합이다.

## 병목과 수정

- HSV 변환 자체는 색상당 반복되지 않았다. 기존 HSV 정리 단계에서 프레임당 관측된 40개 색상에 대해 전체 영상의 연결 요소를 검사했다. Hue LUT는 180 순환 거리와 동률 시 앞 색상 우선 규칙을 유지하며, OpenCV LUT와 절대 차로 S/V를 검사한다. Morphology는 네 번의 형태 연산이 닿을 수 있는 여백을 확보하고, 연결 요소는 그 결과가 존재하는 영역에서만 검사한다. 전체 프레임의 원래 색상 우선순위와 외곽선 좌표도 보존한다.
- 지역 정합의 프로파일 표본은 39개 yaw·축척 변환과 10,878개 XY 후보를 평가했다. 전역은 690개 변환, 5,551,890개 XY 후보를 평가했다. 기존 전역 탐색은 절반 해상도에서 복수 위치 후보를 보존하고, 분리된 최대 6개 가설을 정밀화한다. 지역 탐색은 추적기가 제공한 위치 불확실성과 폭·방향 prior를 사용한다. 후보 개수, 정합·차점 판정 기준은 회귀 검증에서 일치했다.
- 정적 지도 색상 경계를 사전 계산하고, 관측 색상 목록을 프레임당 한 번 만든다. 검색 영역 밖의 지도 색상은 마스크 생성을 건너뛰고, 같은 색이 겹치는 범위의 템플릿만 상관에 전달한다. 가중 정합은 해당 색상의 confidence만 복사한다. 기존 회전·축척 기하 캐시 및 IoU 검색을 재사용한다.
- 조명 보정과 그림자 검출은 종이 샘플과 조명장을 공유한다. 종이 표본이 없는 경우 같은 표본 계산을 되풀이하던 경로를 제거했다. 색 기준의 채널 중앙값은 8비트 히스토그램으로 구한다. 디버그 오버레이는 정합기에서 만든 레이블을 재사용한다.
- 스케줄러는 직전 시작 시각에 설정 주기를 더해 다음 최소 시작 시각을 구한다. 연산이 주기를 넘으면 다음 최신 ID를 바로 선택한다. Windows에서 1ms 미만 대기가 즉시 끝날 수 있어 대기 하한을 두고, 깨어난 뒤 단조 시계를 다시 검사한다. 수신과 재생 소비자는 각자 커서를 사용한다.

## 200ms 변동 조사

과거 결과에서는 0ms 평균 93.13ms, 200ms 평균 206.12ms였다. 새 입력을 사용한 최적화 전 60초 재현에서는 각각 385.91ms와 222.00ms였다. 200ms에만 처리 시간이 늘어나는 패턴은 재현되지 않았다.

0ms와 200ms를 바꿔 8초씩 3회 단기 진단했다. 기본 8스레드에서 200ms의 평균은 짝이 되는 0ms보다 첫 반복에서 약 15ms 높았고, 다음 두 반복에서는 약 8–10ms 낮았다. OpenCV 1스레드에서도 우열이 바뀌었다. 시스템 CPU 샘플에서 이 Python 프로세스 외의 평균 부하는 논리 CPU 전체 대비 약 21–55% 범위였다. 단기 진단의 12개 구간 중 한 구간에서만 GC 수집이 1회 있었다. 부하와 실행 순서가 영향을 줄 수 있음을 확인했지만, 과거 실험의 CPU 주파수·스케줄링 추적과 당시 다른 프로세스 기록이 없어 그 증가의 단일 원인은 확정할 수 없다. [기본 스레드 진단](profiling/baseline_order_threads_8/performance_summary.json) · [1스레드 진단](profiling/baseline_order_threads_1/performance_summary.json)

최적화 후 단독 프로파일에서 OpenCV 기본값(8), 1, 2, 4를 비교했다. 1스레드의 지역 정합 평균이 해당 시험에서 가장 낮았다(각각 38.19, 31.99, 36.01, 36.57ms). OpenBLAS 스레드 환경값을 1로 지정한 10초 시험은 현재 기본 설정보다 빠르지 않았고, 다른 시각에 순차 실행한 진단이어서 그 차이를 OpenBLAS 설정만의 효과로 간주하지 않았다. 정식 반복에는 OpenCV 1스레드를 명시하고 OpenBLAS 환경값은 기본값을 사용했다. [OpenBLAS 기본 진단](profiling/blas_configured/performance_summary.json) · [OpenBLAS 1 진단](profiling/blas_one/performance_summary.json)

## 같은 프로세스의 단계별 교차 비교

단독 프로파일은 실행 시점에 따라 변동이 컸다. 단계 개선율은 해시를 검증한 변경 전 소스와 최종 코드를 같은 프로세스에 올려, OpenCV 1스레드에서 동일 프레임과 prior를 A→B, B→A 순으로 번갈아 30쌍 실행한 결과로 판단했다. 가중 정합은 x축 방향으로 0.35에서 1까지 변하는 합성 confidence를 두 구현에 동일하게 줬다. [변경 전 소스 보관본](baseline/reference_sources.zip) · [30쌍 원본](profiling/paired_stages.json)

| 단계 | 변경 전 평균 / P95 (ms) | 변경 후 평균 / P95 (ms) | 평균 감소 |
| --- | ---: | ---: | ---: |
| HSV | 89.53 / 128.18 | 14.98 / 20.54 | 83.27% |
| 조명·그림자 | 24.05 / 26.58 | 20.52 / 23.86 | 14.65% |
| 지역 정합 | 48.40 / 59.80 | 47.26 / 53.50 | 2.34% |
| 가중 지역 정합 | 57.41 / 73.35 | 50.21 / 63.50 | 12.53% |

같은 프로세스에서 HSV 평균은 20ms 이하와 30% 감소 목표를 달성했다. 지역 정합의 25% 감소 목표는 두 정합 경로 모두 미달했다. 무가중 프로파일에서는 한 지역 정합에 상관 호출이 약 390회 있었다. 변경으로 주변 배열 연산은 줄었으나 정답을 지킬 수 있도록 후보 수와 색상별 상관 계산을 유지했다.

## 처리율과 결과 지연

아래 콜드 비교는 동일 AVI, 기본 OpenCV 8스레드, Unlimited, 워밍업 0초로 각각 60초 실행했다. 두 실행에서 입력은 약 25 FPS였다. 실행별 시스템 부하는 달라질 수 있다.

| 콜드 Unlimited | 추정 FPS | 처리 평균 / P95 (ms) | 결과 지연 평균 / P95 (ms) | 프로세스 CPU |
| --- | ---: | ---: | ---: | ---: |
| 변경 전 | 2.58 | 385.91 / 759.86 | 409.61 / 783.31 | 253.33% |
| 변경 후 | 13.15 | 75.44 / 86.20 | 97.42 / 117.85 | 366.16% |

아래는 4초 워밍업과 OpenCV 1스레드를 사용한 최적화 후 60초 × 3회 측정이다. 각 칸은 반복별 통계의 중앙값이다. P95의 중앙값은 지연 분포를 합쳐 구한 P95와 구분된다.

| 최소 시작 간격 | 추정 FPS | 처리 평균 / P95 (ms) | 결과 지연 평균 / P95 (ms) | 프로세스 CPU | 종료 RSS (MiB) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Unlimited | 17.96 | 55.02 / 80.52 | 76.55 / 107.61 | 99.92% | 71.16 |
| 100ms | 9.15 | 55.97 / 83.79 | 78.99 / 118.99 | 53.17% | 73.64 |
| 150ms | 6.42 | 71.24 / 84.63 | 90.28 / 115.28 | 47.26% | 69.79 |
| 200ms | 4.92 | 41.05 / 58.19 | 61.08 / 85.08 | 22.08% | 74.79 |

이 정지 입력에서 Unlimited는 평균 70ms 이하와 기존 실험 기록 10.68 FPS보다 높은 처리율을 달성했다. 기본 스레드의 최적화 후 콜드 비교(75.44ms)와 150ms의 반복 중앙값(71.24ms)은 70ms 이하 목표에 미달했다. 100ms는 정지 입력에서 CPU 사용 시간을 줄이는 비교 후보이며, 200ms는 결과 한 건의 지연이 낮아도 갱신 횟수와 최신 프레임 사용 비율이 더 낮았다. 200ms의 첫 반복에서는 평균 처리 109.22ms와 P95 결과 지연 241.29ms가 관측됐다. 나머지 두 반복에서 평균 처리는 38.93ms와 41.05ms였다.

기본 설정에서 HSV 평균은 116.63 → 10.97ms, 지역 정합 평균은 201.76 → 50.28ms였다. OpenCV 1스레드 Unlimited 반복에서 각각 8.19ms와 34.75ms였다. CSV 기록 시간의 반복별 평균 중앙값은 약 0.24–0.37ms였으며, 이 시간은 처리 시간 계측 뒤에 발생한다. ## 정확도와 회귀 검증

조명·그림자·높이가 다른 합성 영상 39장에서 변경 전후 마스크 2,995,200픽셀 전체가 일치했다. 지도 정답 건물 픽셀의 평균 색 분류 정확도는 78.70%, 평균 건물 마스크 IoU는 79.64%였다. 두 버전 모두 37장을 채택했고, 채택된 위치의 RMSE는 0.63cm, 평균 yaw 오차는 0.28°, 오측정 채택은 0건이었다. 같은 프레임에서 채택 여부, 거절 이유, 좌표, yaw, 폭, 신뢰 영역이 동일했다. RMSE와 yaw 오차는 채택 관측에서, 성공률은 전체 입력에서 계산했다. [변경 전 마스크와 위치 결과](profiling/baseline/profile.json) · [최종 마스크와 위치 결과](profiling/optimized_final/profile.json)

OpenCV 1스레드 프로파일의 HSV 추적 할당 피크는 3.22 → 1.31 MiB, 프로세스 RSS 샘플은 63.76 → 64.71 MiB였다. 할당 피크는 `tracemalloc`로 관찰한 범위이며 OpenCV 네이티브 메모리 전체를 포함하지 않는다.

자동 테스트 63개가 통과했다. 기존 합성 이동 벤치마크에서 관측은 137개 중 125개를 채택했고, 필터 오차 5cm 이내는 131개, 오측정 채택은 0개, 복구는 4/4회였다. 기본 설정 전후와 반복 측정의 17개 CSV에서 입력 해시, 프레임 ID 순서, 최소 시작 간격, 지연 P95, 프레임 카운트를 검증했다. [통합 CSV](summary.csv) · [통합 JSON](summary.json)

## 실물 XIAO와 UGV

과거의 2.33 FPS와 27.47 FPS는 서로 다른 기록이다. 이번에도 저장된 `:81/stream` 주소는 타임아웃했고 수신한 JPEG는 0개였다. PC에서 COM5는 열거됐지만 현재 IP와 영상은 확인되지 않았다. 정지, 수평 이동, 높이, yaw, 그림자, 복합 장면의 실물 성능은 미검증이다. 실물 기준점을 정할 때 A4 인쇄 지도는 실제 인쇄 폭으로 좌표를 환산한다.

UGV 작업자는 같은 입력 슬롯에서 별도 ID 커서와 실행 주기를 사용할 수 있다. 동시에 실행할 때는 두 작업의 CPU 사용량, RSS, 드롭률과 P95 결과 지연을 함께 측정해야 코어 및 처리 주기를 결정할 수 있다.
